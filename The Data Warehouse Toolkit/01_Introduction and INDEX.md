# 데이터 웨어하우스 설계의 핵심 원리와 실무 적용

## 1. 책의 목적과 저자의 핵심 주장

**결론: 이 책은 원천 데이터를 경영진과 현업 담당자가 쉽게 분석하고 의사결정에 활용할 수 있는 구조로 바꾸는 방법을 설명하는 데이터 웨어하우스 설계 지침서다.**

마트·은행·병원 등 다양한 업종의 사례를 통해 데이터 모델을 어떻게 설계하고 확장해야 하는지 알려준다.

분량이 많아 다음과 같이 나누어 살펴본다.

- 1편: 책의 목적과 저자의 핵심 주장
- 2편: 목차의 전체 흐름과 장별 구성
- 3편: 실무 산출물, 읽는 방법, 자주 하는 오해

예시는 **OO마트(점포 300개, POS·재고·발주·회계 시스템)**로 통일한다.

---

### 1-1. 왜 이 책을 만들었을까?

저자들은 30년 넘게 데이터 웨어하우스를 설계하면서 비슷한 문제가 반복해서 발생하는 것을 경험했다.

예를 들면 다음과 같다.

- 주문일, 출고일, 배송일처럼 하나의 데이터에 날짜가 여러 개 있는 경우
- 상품의 분류 체계가 바뀌어 과거 데이터를 어떻게 관리할지 결정해야 하는 경우
- 회사마다 조직 구조의 깊이가 다른 경우

이러한 문제를 해결하는 방법은 블로그, 컨설팅 경험, 이전 책 등에 흩어져 있었다.

저자들은 이런 문제와 해결 방법을 한 권에 모아 실무에서 찾아볼 수 있도록 정리했다.

즉, 이 책은 처음부터 끝까지 읽는 이론서인 동시에, 실무에서 설계 문제가 발생했을 때 해결 방법을 찾아보는 **설계 기법 참고서**다.

예를 들어 다음과 같은 상황에서 활용할 수 있다.

- 문제: 주문일, 출고일, 배송일을 하나의 팩트 테이블에서 어떻게 관리할까?
- 해결 방법: 날짜 차원을 여러 역할로 사용하는 기법을 찾아본다.
- 참고 위치: 2장의 기법 목록에서 관련 장과 페이지를 확인한다.

### 1-2. 왜 설계자뿐 아니라 팀 전체가 알아야 할까?

데이터 모델의 설계 결정은 이후 개발 단계 전체에 영향을 미친다.

```text
요구사항 수집
     ↓
데이터 모델 설계
     ↓
ETL 개발 및 데이터 적재
     ↓
BI 대시보드 및 분석
```

예를 들어 OO마트의 매출 데이터를 다음과 같이 설계했다고 가정하자.

- 데이터 단위: 하루별 점포별 매출 합계

이렇게 설계하면 각 담당자에게 다음과 같은 영향이 발생한다.

- ETL 개발자: POS 영수증 데이터를 일별로 미리 합산하는 로직을 개발한다.
- BI 개발자: 시간대별 매출 분석에 필요한 원천 수준의 데이터가 없어 차트를 만들기 어렵다.
- 기획자: 오후 3시 타임세일의 매출 효과를 분석할 수 없다.

처음에 데이터 단위를 어떻게 결정했느냐에 따라 이후 개발 결과와 분석 가능 범위가 달라진다.

따라서 데이터 모델링은 설계자만의 업무가 아니다. PM, 데이터 엔지니어, 분석가, 데이터 관리 담당자도 기본 원리를 이해해야 한다.

### 1-3. 분석하기 쉬운 구조와 조회 성능을 함께 고려해야 한다

기존 운영 데이터베이스는 데이터를 중복 없이 관리하기 위해 여러 테이블로 나누어 저장하는 정규화 구조(3NF)를 주로 사용한다.

이 방식은 운영 업무에 적합하다.

- 데이터를 수정할 때 여러 곳을 변경할 필요가 적다.
- 데이터 중복을 줄일 수 있다.
- 입력과 수정 과정에서 데이터 일관성을 유지하기 쉽다.

하지만 분석 업무에서는 불편할 수 있다.

예를 들어 경영진이 다음과 같이 질문한다고 가정하자.

"지난주 강동점 라면 매출은 얼마인가?"

운영계 구조에서는 주문, 상품, 점포, 지역, 상품 분류 등의 테이블을 여러 번 연결해야 답을 구할 수 있다.

```text
[운영계 정규화 구조]

주문상세 → 주문정보 → 점포 → 지역
    |
  상품정보 → 소분류 → 중분류 → 대분류

여러 테이블을 연결해야 분석 가능
```

차원 모델에서는 분석에 필요한 정보를 다음과 같이 구성한다.

```text
          날짜 차원
              |
점포 차원 - 매출 팩트 - 상품 차원
```

사용자는 매출 팩트를 중심으로 날짜, 점포, 상품을 선택해 원하는 데이터를 조회할 수 있다.

저자의 핵심 주장은 두 구조가 담고 있는 데이터 자체가 다른 것이 아니라, 데이터를 저장하고 활용하는 구조가 다르다는 것이다.

**운영계는 데이터를 안정적으로 관리하는 데 초점을 맞추고, 분석계는 데이터를 쉽게 이해하고 조회하는 데 초점을 맞춘다.**

### 1-4. 처음부터 복잡한 구조를 만들지 말아야 한다

저자는 데이터 모델을 설계할 때 불필요한 추상화와 복잡성을 경계한다.

예를 들어 점포, 창고, 고객 주소를 모두 하나의 '위치' 테이블로 관리한다고 가정하자.

처음에는 여러 종류의 위치 정보를 하나로 관리할 수 있어 효율적으로 보인다.

하지만 실제 분석에서는 문제가 생긴다.

- 점포의 지역별 매출을 분석하는 경우
- 고객의 거주 지역별 구매 성향을 분석하는 경우
- 창고의 지역별 재고를 분석하는 경우

모두 위치라는 같은 개념을 사용하지만 분석 대상과 의미는 서로 다르다.

이처럼 지나치게 범용적인 구조를 만들면 사용자가 데이터의 의미를 이해하기 어려워지고, 조회할 때도 불필요한 복잡성이 생긴다.

따라서 처음부터 모든 데이터를 하나의 범용 구조로 통합하기보다 실제 업무에서 사용하는 의미와 목적에 맞게 단순하게 설계해야 한다.

### 1-5. 공통 차원을 활용해 데이터 마트를 점진적으로 확장한다

부서마다 독립적으로 데이터 마트를 만들면 같은 데이터를 서로 다른 기준으로 관리할 위험이 있다.

예를 들어 영업팀과 물류팀이 각각 상품 정보를 관리한다고 가정하자.

| 항목 | 영업팀 마트 | 물류팀 마트 |
|---|---|---|
| 상품 코드 | 8801043 | SKU-1043 |
| 상품 분류 | 라면 | 봉지면 |
| 10월 판매량 | 12,000 | 11,850 |

같은 상품인데도 코드와 분류 기준이 다르다.

이 상태에서는 영업팀의 판매량과 물류팀의 재고 데이터를 정확하게 연결하기 어렵다.

저자는 이를 해결하기 위해 **공통 차원(Conformed Dimension)**을 사용하도록 권장한다.

OO마트에서는 상품 차원을 공통으로 만들고 판매, 재고, 발주 팩트 테이블이 모두 같은 상품 차원을 참조하도록 설계한다.

```text
             상품 차원
            /    |    \
           /     |     \
       판매 팩트 재고 팩트 발주 팩트
```

이렇게 하면 다음과 같은 장점이 있다.

- 여러 업무에서 동일한 상품 기준을 사용한다.
- 판매량과 재고량을 같은 상품 기준으로 비교할 수 있다.
- 처음부터 모든 업무를 한꺼번에 개발하지 않아도 된다.
- 판매 데이터 마트를 먼저 구축한 뒤 재고와 발주 데이터 마트를 순차적으로 추가할 수 있다.

즉, 공통 차원을 기반으로 데이터 마트를 하나씩 구축하면서 전사 데이터 웨어하우스로 확장할 수 있다.

### 1-6. 기술과 비즈니스 양쪽을 이해해야 한다

저자는 데이터 웨어하우스 설계자에게 기술과 비즈니스 양쪽의 이해가 필요하다고 강조한다.

- 기술적 역량(DBA): 테이블 구조, 조인, 인덱스, 조회 성능, 데이터 적재 방식을 이해한다.
- 비즈니스 역량(MBA): 현업에서 어떤 의사결정을 내리기 위해 데이터를 사용하는지 이해한다.

두 가지 중 하나라도 부족하면 잘못된 설계가 나올 수 있다.

예를 들어 다음과 같다.

- 기술만 고려한 경우: 재고 수량을 날짜별로 단순 합산해 잘못된 재고 통계를 제공한다.
- 비즈니스만 고려한 경우: 영수증 10억 건을 매번 여러 테이블과 연결해 조회해야 하는 비효율적인 구조를 만든다.

좋은 데이터 모델은 기술적으로 효율적이면서도 비즈니스 담당자가 원하는 분석을 지원해야 한다.

### 1-7. 기술적으로 완벽해도 현업에서 사용하지 않으면 실패다

저자는 데이터 웨어하우스와 BI 프로젝트의 가장 큰 실패 요인 중 하나로 사용자 수용 부족을 꼽는다.

예를 들어 다음과 같은 상황이다.

1. 기술적으로 완성도 높은 DW를 구축했다.
2. 모든 데이터가 정상적으로 적재된다.
3. 대시보드도 정상적으로 동작한다.
4. 하지만 현업 담당자는 여전히 엑셀로 POS 데이터를 내려받아 분석한다.

왜 이런 일이 발생할까?

컬럼명이 `prd_cat_cd_l3`처럼 현업 담당자가 이해하기 어려운 형태이거나, 실제 업무에서 필요한 분석 기준이 제대로 반영되지 않았기 때문이다.

결국 데이터 웨어하우스는 구축 자체가 목적이 아니다.

현업 담당자가 데이터를 쉽게 이해하고 실제 의사결정에 활용할 수 있어야 성공한 프로젝트다.

### 1-8. 프로젝트는 부서가 아니라 업무 프로세스를 기준으로 나눈다

프로젝트를 부서 단위로 나누면 동일한 원천 데이터를 여러 부서에서 각각 추출하고 가공하는 문제가 발생할 수 있다.

예를 들어 영업팀과 마케팅팀이 각각 POS 데이터를 가져와 별도의 데이터 마트를 만든다고 가정하자.

같은 판매 데이터를 두 번 개발하고 관리하게 된다.

반대로 업무 프로세스를 기준으로 프로젝트를 구성하면 다음과 같이 접근할 수 있다.

- 업무 프로세스: POS 판매
- 데이터 모델: 판매 팩트
- 활용 부서: 영업, 마케팅, 재무

하나의 판매 팩트를 여러 부서가 공통으로 활용할 수 있다.

저자는 업무 프로세스별로 비즈니스 가치와 구현 난이도를 평가하고, 우선순위를 정해 단계적으로 구축할 것을 권장한다.

### 1-9. 1편 핵심 정리

| 구분 | 핵심 내용 | OO마트 사례 |
|---|---|---|
| 책의 목적 | 반복되는 설계 문제와 해결 방법을 정리한 참고서 | 날짜가 여러 개인 주문 처리 |
| 대상 독자 | 설계자뿐 아니라 프로젝트 참여자 전체 | 모델 설계가 ETL과 BI에 미치는 영향 |
| 분석 구조 | 운영계와 분석계는 목적에 맞게 다른 구조를 사용 | 여러 테이블을 연결하는 대신 차원 모델 활용 |
| 단순성 | 불필요한 범용화와 복잡한 구조를 피한다 | 점포·창고·고객 위치를 무조건 하나로 합치지 않기 |
| 공통 차원 | 여러 데이터 마트가 동일한 기준을 공유한다 | 판매·재고·발주가 상품 차원 공유 |
| 기술과 비즈니스 | 조회 효율성과 업무 활용성을 함께 고려한다 | 재고 수량 집계와 조회 성능 |
| 사용자 수용 | 현업에서 실제로 사용해야 성공한 DW다 | 현업이 엑셀 대신 DW를 활용 |
| 프로젝트 단위 | 부서보다 업무 프로세스를 중심으로 구축한다 | POS 판매 팩트를 여러 부서가 공동 활용 |

**핵심 흐름**

운영계 데이터는 분석하기 불편하다 → 차원 모델로 분석하기 쉬운 구조를 만든다 → 공통 차원을 활용해 데이터 마트를 확장한다 → 현업에서 실제로 활용할 수 있어야 성공한다.

## 2. 목차의 전체 흐름과 장별 구성

**결론: 목차 순서는 앞 장의 모델만으로 해결하기 어려운 문제가 다음 장에서 등장하도록 구성되어 있다. OO마트라는 하나의 사례를 따라가면 각 장이 왜 그 순서로 배치되었는지 이해할 수 있다.**

설명이 길어서 3번에 나눠 진행한다.

- 이번: 전체 흐름 + A블록(1–2장) + B블록(3–10장)
- 다음: C·D블록(11–16장)
- 마지막: E·F·G블록(17–21장)

### 2-1. 책 전체의 구성

```text
[A] 1~2장
    데이터 웨어하우스의 기본 개념과 설계 기법
          |
          v
[B] 3~10장
    OO마트 사례를 따라가며
    업무별 데이터 모델 설계 방법 학습
          |
          v
[C] 11장
    설계한 데이터 모델 검토
          |
          v
[D] 12~16장
    다른 업종의 데이터 모델에 적용
          |
          v
[E] 17~18장
    프로젝트 진행 및 설계 관리 방법
          |
          v
[F] 19~20장
    ETL을 통한 실제 데이터 적재
          |
          v
[G] 21장
    빅데이터 환경으로 확장
```

- 판매 시스템: POS

## 3. A블록 (1~2장): 기본 개념과 설계 기법

### 3-1. 1장 Primer: 데이터 웨어하우스의 기본 개념

첫 장에서는 운영계와 분석계의 차이를 이해하고, 데이터 웨어하우스의 기본 구조를 설명한다.

OO마트를 예로 들면 다음과 같다.

- POS는 영수증 한 건을 빠르게 저장하고 처리하는 데 최적화되어 있다.
- 경영진은 지난주 강동점의 라면 매출이 전주보다 얼마나 증가했는지 알고 싶어 한다.
- 이 질문에 답하려면 수많은 영수증 데이터를 모아 계산해야 한다.

운영계는 현재 업무를 처리하는 데 초점을 맞추지만, 분석계는 과거 데이터를 보관하고 다양한 관점에서 비교할 수 있도록 설계한다.

이를 위해 먼저 두 가지 기본 개념을 이해해야 한다.

- 팩트(Fact): 매출액, 판매 수량, 재고 수량처럼 측정하고 분석할 값
- 차원(Dimension): 날짜, 점포, 상품처럼 측정값을 설명하고 구분하는 기준

이 개념을 알아야 이후의 데이터 모델 설계를 이해할 수 있다.

### 3-2. 2장 기법 개요: 전체 설계 기법 찾아보기

2장은 이후에 등장하는 다양한 데이터 모델링 기법을 미리 정리해 놓은 목록이다.

각 기법이 어느 장에서 설명되는지와 관련 페이지를 안내한다.

처음부터 순서대로 공부하기보다는 실무에서 특정 문제가 발생했을 때 찾아보는 참고 자료로 활용하면 좋다.

예를 들어 SCD Type 6의 개념이나 적용 방법이 궁금하다면 2장에서 해당 기법의 위치를 확인하고 관련 장으로 이동하면 된다.

## 4. B블록 (3~10장): OO마트의 업무를 따라가며 배우는 설계 기법

이 블록의 핵심은 업무가 하나씩 추가될 때마다 새로운 데이터 모델링 문제가 발생한다는 점이다.

처음에는 판매 데이터만 설계하면 되지만, 재고와 발주가 추가되면 기존 구조만으로 해결하기 어려운 문제가 나타난다.

저자는 이러한 문제를 업무별 사례를 통해 하나씩 설명한다.

### 4-1. 3장 Retail Sales: 첫 번째 매출 팩트 테이블 만들기

**상황: OO마트의 POS 판매 데이터를 분석하기 위한 첫 번째 데이터 모델을 만든다.**

가장 먼저 결정해야 하는 것은 데이터의 저장 단위인 그레인(Grain)이다.

그레인은 팩트 테이블의 한 행이 무엇을 의미하는지 정의하는 기준이다.

예를 들어 다음과 같은 판매 데이터가 있다고 가정하자.

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-31 |
| 점포 | 강동점 |
| 상품 | 신라면 5입 |
| 행사 | 1+1 행사 |
| 영수증 번호 | R-883021 |
| 판매 수량 | 2개 |
| 판매 금액 | 7,800원 |

이 데이터를 일별 점포별 매출 합계로 저장할 수도 있지만, 그러면 개별 영수증이나 시간대별 판매 내역을 분석하기 어렵다.

따라서 이 장에서는 **영수증의 상품 판매 한 줄을 데이터 한 건으로 저장하는 방식**을 다룬다.

이렇게 하면 나중에 날짜별, 점포별, 상품별, 시간대별로 원하는 수준까지 합산할 수 있다.

주요 학습 내용은 다음과 같다.

- 데이터 모델을 설계하는 4단계 방법
- 거래 한 건을 기록하는 팩트 테이블
- 날짜 차원
- 영수증 번호처럼 별도의 차원 테이블을 만들지 않고 팩트에 직접 보관하는 값(비정규 차원, Degenerate Dimension)

### 4-2. 4장 Inventory: 판매 데이터와 재고 데이터는 다르게 설계해야 한다

**상황: 판매 데이터에 이어 재고 데이터를 추가한다.**

여기서 기존 매출 모델로는 해결할 수 없는 문제가 발생한다.

매출은 여러 건을 합산해 총매출을 구할 수 있지만, 재고는 날짜별로 단순 합산할 수 없다.

예를 들어 다음과 같다.

| 날짜 | 재고 수량 |
|---|---:|
| 10월 30일 | 100개 |
| 10월 31일 | 90개 |

두 날짜의 재고를 더한 190개는 의미 있는 재고 수량이 아니다.

재고는 특정 시점의 상태를 나타내기 때문이다.

이를 해결하기 위해 매일 특정 시점의 재고 상태를 기록하는 **기간별 스냅샷 팩트(Periodic Snapshot Fact)**를 사용한다.

이때 알아야 할 개념이 반가산성(Semi-additive)이다.

- 점포 방향으로는 재고 수량을 합산할 수 있다.
- 날짜 방향으로는 재고 수량을 단순 합산할 수 없다.

여기서 또 다른 문제가 등장한다.

판매팀과 재고팀이 서로 다른 상품 기준을 사용한다면 판매량과 재고량을 정확하게 비교하기 어렵다.

따라서 이 장에서는 다음 개념을 다룬다.

- 데이터 마트 전체의 업무 범위와 차원 공유 관계를 정리하는 버스 매트릭스(Bus Matrix)
- 여러 업무에서 공통으로 사용하는 차원(Conformed Dimension)

**순서의 이유:** 판매 데이터에 이어 두 번째 업무인 재고 데이터가 추가되면서 여러 데이터 마트가 동일한 차원을 공유해야 한다는 문제가 드러난다.

### 4-3. 5장 Procurement: 공통으로 사용하는 상품 정보가 바뀐다면?

**상황: 공급사 발주 데이터를 추가한다.**

판매와 재고에 이어 발주 데이터까지 추가되면 상품 차원을 세 가지 업무에서 공유하게 된다.

이때 상품의 속성이 변경되는 문제가 발생한다.

예를 들어 상품 분류가 다음과 같이 바뀌었다고 가정하자.

- 2026년 9월 1일 이전: 신라면의 분류는 '라면'
- 2026년 9월 1일 이후: 신라면의 분류는 '봉지면'

그렇다면 작년 매출을 분석할 때 어떤 분류를 사용해야 할까?

- 과거 매출도 새로운 분류인 '봉지면'으로 표시할 것인가?
- 과거 매출은 당시 분류인 '라면'으로 유지할 것인가?

이러한 문제를 해결하는 방법이 변경 이력 관리(SCD, Slowly Changing Dimension)다.

대표적인 방식은 다음과 같다.

- Type 1: 기존 값을 새로운 값으로 덮어쓴다. 과거 변경 이력은 보존하지 않는다.
- Type 2: 변경된 값을 새로운 행으로 추가한다. 과거 시점의 속성도 그대로 보존한다.

이 장에서는 SCD Type 0~7을 다룬다.

**순서의 이유:** 상품 차원을 여러 업무에서 공유하게 된 다음에 상품 정보의 변경 이력을 어떻게 관리할지 배우도록 구성되어 있다.

### 4-4. 6~10장: 다양한 업무를 통해 더 복잡한 설계 문제 배우기

이후 장에서는 OO마트의 다른 업무를 추가하면서 다양한 데이터 모델링 기법을 설명한다.

| 장 | 업무 | 새롭게 발생하는 문제 | 주요 설계 기법 |
|---|---|---|---|
| 6장 | 주문 관리 | 주문일, 출고일, 배송일 등 여러 날짜를 하나의 팩트에서 관리해야 한다. | 역할별 날짜 차원 |
| 6장 | 주문 관리 | 배송비는 주문 전체에 부과되지만 데이터는 상품별로 저장된다. | 주문 단위 금액을 상품별로 배분 |
| 7장 | 회계 | 조직마다 계층의 깊이가 다르다. | 불규칙한 계층 구조, 연결 테이블 |
| 8장 | 고객 관리 | 고객 한 명이 여러 관심사를 가질 수 있다. | 다중값 연결 테이블 |
| 9장 | 인사 관리 | 직원 정보의 변경 이력 자체를 분석해야 한다. | 팩트처럼 활용하는 차원 |
| 10장 | 금융 | 예금과 대출처럼 공통 속성과 개별 속성이 다른 데이터가 존재한다. | 상위 유형과 하위 유형 구조 |

각 장에서 다루는 문제를 조금 더 살펴보자.

**6장 주문 관리**

하나의 주문에는 주문일, 출고일, 배송일처럼 서로 다른 의미의 날짜가 존재한다.

날짜 차원 하나를 여러 역할로 연결해 사용하는 방법을 배운다.

또한 주문 전체에 부과된 배송비를 상품별 주문 데이터에 어떻게 배분할지도 다룬다.

**7장 회계**

조직 구조가 항상 같은 깊이로 구성되는 것은 아니다.

예를 들어 다음과 같은 구조가 있을 수 있다.

- 본사 → 지역본부 → 점포
- 본사 → 직영점

이처럼 조직마다 계층의 깊이가 다른 경우 이를 어떻게 표현하고 분석할지 배운다.

**8장 고객 관리**

고객 한 명이 육아, 캠핑, 여행 등 여러 관심사를 가질 수 있다.

하나의 고객이 여러 값을 가지는 관계를 데이터 모델에서 어떻게 표현할지 배운다.

**9장 인사 관리**

직원의 소속 부서나 직급은 시간에 따라 변경된다.

이때 직원 정보의 변경 이력 자체를 분석 대상으로 다루는 방법을 배운다.

**10장 금융**

예금과 대출은 서로 다른 상품이지만 계좌번호, 고객번호, 개설일 등 공통으로 관리할 수 있는 속성도 있다.

공통 속성과 개별 속성을 구분해 상위 유형과 하위 유형으로 모델링하는 방법을 배운다.

### 4-5. B블록의 전체 흐름

| 순서 | 장 | 새롭게 등장하는 설계 문제 |
|---|---|---|
| 첫 번째 | 3장 판매 | 매출 데이터를 어떤 단위로 저장할 것인가? |
| 두 번째 | 4장 재고 | 재고처럼 날짜 방향으로 합산할 수 없는 데이터는 어떻게 저장할 것인가? |
| 세 번째 | 4장 재고 | 판매와 재고가 같은 상품 기준을 사용하려면 어떻게 해야 하는가? |
| 네 번째 | 5장 발주 | 여러 업무에서 공유하는 상품 정보가 변경되면 어떻게 관리할 것인가? |
| 다섯 번째 | 6~10장 | 여러 날짜, 불규칙한 계층, 다중값, 변경 이력, 서로 다른 상품 유형은 어떻게 모델링할 것인가? |

**핵심 흐름**

첫 번째 업무인 판매 데이터를 모델링한다 → 재고 데이터가 추가되면서 공통 차원의 필요성을 이해한다 → 발주 데이터까지 추가되면서 차원의 변경 이력을 관리해야 한다 → 이후 다양한 업무를 통해 복잡한 데이터 관계를 표현하는 방법을 배운다.

## 5. 지금까지의 핵심 정리

이 책의 앞부분은 단순히 데이터 모델링 기법을 나열하는 방식이 아니다.

OO마트라는 하나의 기업을 기준으로 업무가 확장될 때마다 새로운 설계 문제가 발생하고, 그 문제를 해결하는 방법을 차례대로 익히도록 구성되어 있다.

| 구분 | 학습 내용 | 핵심 질문 |
|---|---|---|
| 1장 | 데이터 웨어하우스 기본 개념 | 운영계와 분석계는 왜 다른가? |
| 2장 | 설계 기법 목록 | 필요한 기법은 어디에서 찾아볼 수 있는가? |
| 3장 | 판매 데이터 모델 | 팩트 테이블의 한 행은 무엇을 의미하는가? |
| 4장 | 재고 데이터 모델 | 재고처럼 합산 방식이 다른 데이터는 어떻게 관리하는가? |
| 5장 | 발주 데이터 모델 | 공통 차원의 변경 이력은 어떻게 관리하는가? |
| 6~10장 | 주문·회계·고객·인사·금융 | 복잡한 데이터 관계를 어떻게 표현하는가? |

**전체 학습 방향**

기본 개념 이해 → 첫 번째 팩트 설계 → 여러 업무의 차원 공유 → 데이터 변경 이력 관리 → 복잡한 데이터 관계 모델링
