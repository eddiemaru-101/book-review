# 1. 책의 목적과 저자의 핵심 주장

**결론: 이 책은 "원천 데이터를 경영진이 바로 질문할 수 있는 구조로 바꾸는 방법"을 마트·은행·병원 같은 사례로 가르치는 설계 교과서다.**

분량이 많아서 2번에 나눠 진행한다.

- 이번: 1. 책의 목적, 2. 저자의 핵심 주장
- 다음: 3. 실무 산출물, 4. 읽는 방법, 5. 5가지 오해

예시는 앞 답변과 같은 **OO마트(점포 300개, POS·재고·발주·회계 시스템)**로 이어간다.

---

## 1. 저자가 밝힌 책의 목적

### 1-1. “one-stop shop”이라는 뜻

- 배경
  - 저자들은 30년 넘게 같은 설계 문제가 반복되는 것을 봤다.
  - 예: 날짜가 3개인 주문, 바뀌는 상품 카테고리, 깊이가 다른 조직도 등
  - 이런 해법이 블로그 글, 컨설팅 경험, 이전 판에 흩어져 있었다.
- 그래서 이 책은 해법을 한 권에 모은 **패턴 카탈로그**다.
- 실무에서 쓰는 방식
  - 문제: "주문일·출고일·배송일을 한 팩트에 어떻게 넣지?"
  - 책에서 찾는 것: 2장 목록 → role-playing 차원 → 6장 해당 페이지

### 1-2. 왜 팀 전원이 알아야 하나

모델 하나가 프로젝트 전 단계에 영향을 준다.

```text
요구사항 수집 → 차원 모델 → ETL → BI 대시보드
                (grain 결정)  (적재)  (화면)
```

- 예시: 매출 팩트의 grain을 "일별 점포별 합계"로 정한 경우
  - ETL 개발자: 영수증을 미리 합산하는 로직을 짠다.
  - BI 개발자: 시간대별 차트를 만들 수 없다.
  - 기획자: "오후 3시 타임세일 효과"를 분석할 수 없다.
- 모델러 한 명의 결정이 모든 역할에 영향을 준다. 그래서 대상 독자를 설계자뿐 아니라 PM, 분석가, 데이터 스튜어드까지로 넓혔다.

## 2. 저자의 핵심 주장

### 2-1. 이해 가능성 + 쿼리 성능

- 등장 배경: 정규화 모델(3NF)의 한계
  - 3NF는 중복을 없애려고 데이터를 잘게 쪼갠다.
  - 운영계에서는 장점이다. 수정할 때 한 곳만 바꾸면 되기 때문이다.
  - 분석계에서는 문제가 된다. 저자는 3NF를 “LA 고속도로 지도”에 비유하는데, 사용자가 이해하지 못하고 DB 옵티마이저도 복잡한 조인을 감당하기 어렵다는 뜻이다.
- 예시: "지난주 강동점 라면 매출" 질문

```text
[3NF] 주문라인 → 주문헤더 → 점포 → 지역
          ↓
        상품 → 소분류 → 중분류 → 대분류
  조인 7개 이상, 사용자가 직접 못 짬

[차원 모델]
        날짜차원
           |
점포차원 - 매출팩트 - 상품차원
  조인 3개, 필터만 고르면 됨
```

- 저자 주장: 두 모델이 담은 정보는 같다. 데이터를 "포장하는 방식"만 다르다.

### 2-2. 단순성 지키기

- 저자 표현: 처음부터 복잡하게 시작한 모델은 끝에 가면 더 복잡해진다.
- 결과: 쿼리가 느려지고 사용자가 외면한다.
- 실무 예시
  - 모델러가 "위치"라는 범용 차원 하나에 점포·창고·고객 주소를 모두 넣는 경우
  - 분석가가 "점포의 시·도"와 "고객의 시·도"를 구분하지 못한다.
  - 저자는 이런 추상화를 2장에서 피해야 할 패턴으로 명시한다.

### 2-3. conformed dimension으로 점진적 확장

- 등장 배경: 부서별 데이터 마트(independent data mart)의 한계
  - 영업팀과 물류팀이 각자 원천에서 데이터를 따로 추출한다.
- 예시: 같은 상품의 정의가 다르다.

| 항목 | 영업팀 마트 | 물류팀 마트 |
|---|---|---|
| 상품 코드 | 8801043 | SKU-1043 |
| 카테고리 | 라면 | 봉지면 |
| 10월 판매량 | 12,000 | 11,850 |

- 결과: 임원 회의에서 숫자 맞추는 데 시간을 쓴다.
- 해결: 상품 차원 하나를 만들고 판매·재고·발주 팩트가 모두 공유한다.
- 장점: 한 번에 다 만들 필요가 없다. 판매부터 만들고 재고를 붙여도 상품 차원이 같으니 바로 비교할 수 있다.

### 2-4. 반은 DBA, 반은 MBA

- DBA 역량: 조인 성능, 인덱스, 적재 방식을 이해하는 것
- MBA 역량: "이 숫자로 어떤 의사결정을 하는가"를 이해하는 것
- 예시
  - 기술만 아는 경우: 재고 수량을 날짜 방향으로 SUM해서 잘못된 값을 보여준다.
  - 비즈니스만 아는 경우: 영수증 10억 행에 매번 풀스캔하는 구조를 만든다.

### 2-5. 실패 원인은 사용자 수용

- 저자의 10대 함정 중 1위: DW/BI 성공이 사용자 수용에 달렸다는 것을 무시하는 것
- 예시
  - 기술적으로 완벽한 DW를 만들었다.
  - 현업은 여전히 엑셀로 POS 데이터를 직접 내려받는다.
  - 이유: 컬럼명이 `prd_cat_cd_l3`라서 무슨 뜻인지 모른다.
- 결과: 투자는 했지만 의사결정에 쓰이지 않아 실패로 끝난다.

### 2-6. 프로젝트 단위 = 업무 프로세스

- 부서 단위로 잡으면: 영업팀 마트와 마케팅팀 마트가 같은 POS 데이터를 두 번 추출한다.
- 프로세스 단위로 잡으면: “POS 판매” 팩트 하나를 영업·마케팅·재무가 같이 쓴다.
- 저자 권고: 프로세스별로 비즈니스 가치와 구현 난이도를 매기고, 둘 다 높은 것부터 착수한다.

## 정리

| 항목 | 핵심 | OO마트 예시 |
|---|---|---|
| 목적 | 반복되는 설계 문제의 해법 모음 | 날짜 3개 문제 → 6장 |
| 대상 | 팀 전원 | grain 결정이 ETL·BI에 전파 |
| 이해·성능 | 3NF 대비 조인 단순화 | 조인 7개 → 3개 |
| 단순성 | 범용 추상화 금지 | "위치" 차원 하나로 합치지 않기 |
| conformed | 차원 공유로 점진적 확장 | 상품 차원 하나를 판매·재고가 공유 |
| 사용자 수용 | 안 쓰이면 실패 | 컬럼명 `prd_cat_cd_l3` |
| 프로세스 단위 | 부서별 중복 추출 방지 | POS 판매 팩트 하나 |

**핵심 흐름:** 3NF는 분석에 불편 → 차원 모델로 단순화 → 차원을 공유해 전사로 확장 → 사용자가 써야 성공



# 2. 목차의 전체 흐름과 장별 구성

**결론: 목차 순서는 앞 장의 모델로는 풀리지 않는 문제가 다음 장에서 생기도록 배치돼 있다. 마트 체인 하나를 예로 따라가면 순서의 이유가 보인다.**

설명이 길어서 3번에 나눠 진행한다.

- 이번: 큰 그림 + A블록(1–2장) + B블록(3–10장)
- 다음: C·D블록(11–16장)
- 마지막: E·F·G블록(17–21장)

---

## 전체 흐름

```text
[A] 1-2장  용어와 기본 구조
     |
     v
[B] 3-10장  마트 하나를 따라가며
     |      장마다 새 문제 → 새 기법
     v
[C] 11장   만든 설계 검토하기
     |
     v
[D] 12-16장 다른 업종에 재조합
     |
     v
[E] 17-18장 프로젝트 진행 방법
     |
     v
[F] 19-20장 ETL로 실제 적재
     |
     v
[G] 21장   빅데이터로 확장
```

## 예시 설정 (가상 데이터)

- 도메인: OO마트 체인, 점포 300개
- 원천 시스템: POS(판매), WMS(재고), 발주 시스템, ERP(회계)
- 목표: 경영진이 보는 매출·재고·수익성 분석 DW

---

## 1. A블록 (1–2장): 왜 맨 앞인가

### 1-1. 1장 Primer

- 다루는 내용: 운영계(OLTP)와 분석계(DW)는 목적이 다르다는 것
- 예시
  - POS는 영수증 1건을 빠르게 저장하는 데 최적화돼 있다.
  - 경영진의 질문은 "지난주 강동점 라면 매출이 전주 대비 몇 % 늘었나"다.
  - 이 질문은 영수증 수십만 건을 훑어서 합쳐야 답할 수 있다.
- 운영계는 현재 상태만 덮어쓰고, 분석계는 이력을 보관한다.
- 그래서 팩트(측정값)와 차원(설명 정보)이라는 용어를 먼저 정의한다.

### 1-2. 2장 기법 개요

- 뒤에 나올 기법 전체를 미리 모아 둔 목록이다. 기법마다 해당 장과 페이지를 표시한다.
- 처음부터 읽는 장이 아니다. 실무에서 "SCD Type 6이 뭐였지?" 할 때 찾아보는 사전이다.

---

## 2. B블록 (3–10장): 마트를 따라가는 순서

핵심은 장마다 **이전 모델로 풀 수 없는 문제**가 하나씩 생긴다는 점이다.

### 2-1. 3장 Retail Sales: 첫 번째 팩트 테이블

- 상황: POS 판매 데이터로 첫 모델을 만든다.
- 결정할 것: grain(팩트 1행이 무엇을 뜻하는지)
- 예시 행
  - 날짜=2026-10-31
  - 점포=강동점
  - 상품=신라면 5입
  - 프로모션=1+1 행사
  - 영수증번호=R-883021
  - 수량=2, 금액=7,800

- grain을 영수증 라인 1건으로 잡는 이유
  - 일별 합계로 저장하면 "1+1 행사 상품이 몇 시에 많이 팔렸나"를 볼 수 없다.
  - 가장 잘게 저장해야 나중에 어떤 방향으로든 합산할 수 있다.

- 이 장에서 배우는 기법: 4단계 설계, 트랜잭션 팩트, 날짜 차원, degenerate 차원(영수증번호)

### 2-2. 4장 Inventory: 판매 모델로는 재고를 못 담는다

- 문제: 재고 수량은 판매 금액처럼 더할 수 없다.
  - 10/30 재고 100개 + 10/31 재고 90개 = 190개라는 값은 의미가 없다.
  - 날짜 방향으로는 합산할 수 없고 점포 방향으로만 합산할 수 있다. 이것을 semi-additive라고 한다.
- 해결: 매일 재고 상태를 찍어 두는 periodic snapshot 팩트를 쓴다.
- 더 중요한 문제
  - 판매팀의 상품 테이블과 재고팀의 상품 테이블이 다르면 "재고 회전율 = 판매 / 재고"를 계산할 수 없다.
  - 그래서 이 장에서 버스 매트릭스와 conformed dimension(공유 차원)을 처음 다룬다.
- 순서 이유: 두 번째 프로세스가 생겨야 "차원 공유" 문제가 드러난다.

### 2-3. 5장 Procurement: 공유 차원이 바뀌면?

- 상황: 공급사 발주 데이터를 추가한다. 가치사슬로 보면 재고보다 한 단계 상류다.
- 문제: 상품 속성이 바뀐다.
  - 2026-09-01 이전: 신라면 카테고리 = "라면"
  - 2026-09-01 이후: 카테고리 = "봉지면"
  - 작년 매출을 옛 카테고리로 볼지, 새 카테고리로 볼지 정해야 한다.
- 해결: SCD Type 0–7
  - Type 1: 덮어쓴다. 과거 이력은 사라진다.
  - Type 2: 새 행을 추가한다. 과거 매출은 옛 카테고리로 남는다.
- 순서 이유 (해석): 차원을 판매·재고·발주 세 팩트가 공유하게 된 시점이다. 차원 변경의 영향이 가장 커진 뒤에 SCD를 다룬다.

### 2-4. 6–10장: 남은 기법을 업무 하나씩으로 도입

| 장 | 새로 생기는 문제 (예시) | 도입 기법 |
|---|---|---|
| 6 Order | 주문일·출고일·배송일 3개 날짜가 한 행에 있다 | role-playing 차원 |
| 6 Order | 배송비 3,000원이 주문 헤더에만 있다 | 헤더 값을 라인에 배분 |
| 7 Accounting | 조직 계층 깊이가 다르다 (본사→지역→점포, 본사→직영점) | ragged hierarchy, bridge table |
| 8 CRM | 고객 1명에게 관심사가 여러 개다 (육아, 캠핑) | 다중값 bridge, study group |
| 9 HR | 직원 차원의 변경 이력 자체가 분석 대상이다 | 팩트처럼 동작하는 차원 |
| 10 Financial | 예금과 대출의 속성이 서로 다르다 | supertype / subtype |

- 순서 경향: 단일 값 차원에서 계층, 다중값, 이종 상품 순서로 차원의 복잡도가 올라간다.
- 6장이 먼저 오는 이유: 저자가 주문관리를 "DW/BI에서 가장 먼저 구현되는 경우가 많은 영역"으로 소개한다.

## 정리

| 블록 | 장 | 예시로 본 핵심 |
|---|---|---|
| A | 1–2 | POS와 DW의 목적이 달라서 팩트와 차원을 정의한다 |
| B | 3 | 영수증 라인 단위 grain |
| B | 4 | 재고는 날짜로 합산 불가, 상품 차원 공유 |
| B | 5 | 공유 차원의 속성 변경은 SCD로 처리 |
| B | 6–10 | 날짜 역할, 계층, 다중값, 이종 상품 |

**핵심 흐름:** 첫 팩트 → 두 번째 팩트에서 차원 공유 → 공유 차원의 변경 → 더 복잡한 차원 순서다.

매 장 직전 모델로는 풀 수 없는 문제가 등장하기 때문에 이 순서로 읽어야 한다.
